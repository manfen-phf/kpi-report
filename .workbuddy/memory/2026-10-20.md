## 追加（10:15）：修正 S1 预估的剩余天数 bug（重要）

**用户反馈**：预估完成版的星期对星期外推不对。
- 10/19 是未有数据日 → 应按 **10/12**（同周一）订单量取数
- 10/20 → 按 **10/13**，以此类推直到月底
- 用户手算玉林月末 ≈ **372,849 单 / 102.33%**
- 报告却显示 **130.81%** ❌

### 根因：`project_s1()` 剩余天数算错
```python
last_i = len(dates) - 1        # = 9（观测日的个数！10/08~10/18 共10天）
remain = MONTH_DAYS - last_i  # = 31 - 9 = 22 ❌ 实际应该是 13 天
```
正确写法：
```python
remain = MONTH_DAYS - last.day   # = 31 - 18 = 13 ✓
```
→ 原实现外推到了 **10/40**（10月只有31天），凭空多算 9 天，完成率虚高约 28pp。

### 严格按 D-7 链实现
```python
for back in (7, 14, 21, 28):        # 同一星期几逐周回退
    src = dt - timedelta(days=back)
    if src 有数据: v = 该日单量; break
# 全部回退无果 → 近 7 天日均兜底
```
- 10/19(周一) → 10/12、10/20(周二) → 10/13 …… 与用户描述完全一致

### 验证方法（重要，值得复用）
写脚本用 **6 种候选算法**逐一计算玉林月末值，与用户手算比对：
| 算法 | 月末 | 完成率 |
|---|---|---|
| V1 D-7链(回退14/21/28) | 372,811 | 102.32% ★ |
| V2 近7日同星期几 | 372,811 | 102.32% ★ |
| V3 近7观测日同星期几 | 372,811 | 102.32% ★ |
| V4 D-7链+日均兜底 | 372,811 | 102.32% ★ |
| V5 同星期几取最近观测 | 372,811 | 102.32% ★ |
| V6 全部观测同星期均值 | 371,485 | 101.96% |
→ **多种算法都命中同一值**，证明算法本身没错，**纯粹是剩余天数算错**。
修正后报告值 372,811 / 102.32%，与用户手算 372,849 / 102.33% 差 38 单（取整误差）。

### 修正后 8 城预估完成率

博白 105.11% / 田东 99.07% / 东兰 122.85% / 凤山 132.95%

### 教训
- **「剩余天数」一律用 `last.day`（日号），不要用 `len(dates)-1`（观测日个数）**。

## 追加（11:55）：负向权益完成率分母错误（重要，影响所有罚款判定）

**用户反馈**：预估版负向权益数据不对 —— 钦州/博白 结果指标完成率≥105%，则过程仅需≥60%就无罚款。

### 根因：分母写成了 权重×1.2
```python
res_rate  = score_result / (40 * 1.2)   # 分母 48 ❌
proc_rate = score_proc   / (60 * 1.2)   # 分母 72 ❌
```
官方原文：**完成率 = 合计得分 /（合计权重 × 100）** → 分母是**权重本身**（40 / 60）。

### 用 legacy 反向验证（关键方法）
legacy 实际版玉林：过程得分 32.47，页面显示完成率 **54.1%**
- 32.47 / 60 = **54.1%** ✓
- 32.47 / 72 = 45.1% ✗ 与页面不符

→ 确认分母是 60。**这是判断「显示对不对」最直接的证据：拿 legacy 的得分和页面上显示的完成率反算分母。**

### 影响面
- 过程完成率整体被低估 20%（除以72 而非 60）
- 罚款触发线 90% 等价于「过程得分 < 54 分」，用72 时实际卡在 64.8 分，**门槛偏高约 11 分**
- 减免条件「过程≥60%」用 72 时实际卡在 43.2 分，**门槛偏低约 7 分** → 双重错位

## 追加（15:35，10-21）：修复 update.bat 双击闪退

**用户反馈**：「用哪个程序一键更新」→「双击闪退」

### 根因（两个叠加）
1. **文件是 LF 行尾**（0 CRLF / 40 裸 LF）
   cmd.exe 解析 bat 依赖 CRLF，LF 会导致解析错乱 → 直接闪退
   原因：Write 工具写出的文件是 LF
2. **UTF-8 无 BOM + cmd 按 GBK 解析**
   `chcp 65001` 只影响后续子进程输出，**对 bat 自身解析无效**
   → 中文乱码，甚至被当成命令执行：
     `'文件' 不是内部或外部命令` / `'level'` / `'/b'` / `'loy_api.py"`

### 修复
- 全文改纯 ASCII（0 个非 ASCII 字节）
- 行尾统一 CRLF（46 行全 CRLF，0 裸 LF）
- 保留 `chcp 65001`（对 Python 子进程输出仍有用）
- 提示文案改英文，新增「预计 3-4 分钟」避免用户以为卡死

### 验证：端到端实测跑通
```
[1/2] report_data.py 成功（自动取到 10-21 更新的文件，数据截至 10-20）
[2/2] _deploy_api.py 成功（OK: 1 commit 792eaa83b5, files: 11）
```

### ⚠️ Windows bat 编写规范（已写入 README）
1. **行尾必须 CRLF** —— 工具重写后要显式转换：
   ```python
   raw = open('update.bat','rb').read().replace(b'\r\n',b'\n').replace(b'\n',b'\r\n')
   open('update.bat','wb').write(raw)
   ```
2. **内容必须纯 ASCII** —— 中文提示放 README，不要放 bat
3. `chcp 65001` 不能替代文件本身的编码正确性

### 踩坑：git 分叉处理
- `_deploy_api.py` 走 GitHub API 直接提交，**本地 git 会落后于远端**
- 结果本地 commit 与远端 commit 并行 → `git pull --rebase` 在 data.js 上冲突
- **教训**：`_deploy_api.py` 与本地 `git push` 并存时，
  提交前先 `git fetch && git status` 看远端领先多少，
  不要盲目 rebase（data.js 冲突无意义，因为线上才是新的）
- 最终解法：`git checkout -- data.js` 丢弃过时本地副本 → merge → `git add -A` 一次性提交
  （会连带把行尾差异一起提交，diff 看着很大但内容一致）

### 顺带：git 行尾警告
仓库里 `.gitattributes` 已配 `*.bat text eol=crlf`，但**仓库内实际存的是 LF**
（git 规范做法：`eol=crlf` 只影响工作区，仓库内统一存 LF）。
换台机器 clone 时会自动转 CRLF，所以不影响正常使用。
但**本机若用工具重写 bat，必须自己保证 CRLF**，否则立刻闪退。
